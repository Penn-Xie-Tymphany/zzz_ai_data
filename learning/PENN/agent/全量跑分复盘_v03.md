## 6. 失败归因

### 6.1 未提交 2 题（API 超时，非架构）

- `task_80`（easy）、`task_173`（medium）：`APITimeoutError: Request timed out.`
- 属网络抖动，重试未覆盖该异常类型；**且暴露单题超时未生效的 bug**（见 §8）。

### 6.2 "列对但 recall=0"（值算错）20 题

> 特征：**列数大多已对（gc==pc 或接近），但值不对**。说明 Planner 的契约切得准，败在子 Agent 的执行/计算。

### 6.3 根因假设（待看 trace 验证）

- `worker_max_steps=8` / `worker_total_steps=36` 对 medium/hard 的复杂聚合偏紧，子 Agent 中途 `finish` 返回不完整/未校验结果；
- 子 Agent 计算 prompt 偏弱（缺"先算中间量、再拼答案"的强约束）；
- 单条 observation 截断 3000 字符，复杂表预览被截导致计算依据不足；
- 部分题需多源 join，子 Agent 间通过 `WorkerResult` 传值可能丢失精度/上下文。

## 7. v0.4 优化主线（执行质量）

1. **预算上调 + 诊断**：`worker_max_steps` 8→12、`worker_total_steps` 36→60，先观分数变化；
2. **子 Agent 计算 prompt 强化**：要求先产出可验证的中间量（SQL/Python 结果片段），再合成答案；
3. **关键中间量回传校验**：Composer 拼表前校验子任务 `artifacts` 是否齐全；
4. **observation 截断策略细化**：对 CSV/SQL 预览按列采样而非盲目截断前 3000 字符；
5. **同 harness ReAct 对照**：`run_benchmark.py --mode react` 跑一遍，拿到同代码、同模型的公平对照分。

## 8. 已知 bug（必须修）

- **单题超时未生效**：`RunConfig.task_timeout_seconds=1800` 在 `runner.run_one` 没有落地，单题无受控超时。
  这次最后 2 题（task_80/173）卡到 API 超时而非受控失败，且拖慢整批收尾。
  **修复**：`run_one` 用 `ThreadPoolExecutor`/`future.result(timeout=task_timeout_seconds)` 兜底，超时即判未提交（不中断其他题）。
- **API 超时（网络抖动）**：`LLMClient` 已通过 openai 客户端 `max_retries` 覆盖 `APITimeoutError`（重试 2 次）；task_80/173 是重试后仍失败，属网络抖动。下一步可对超时题做**单题重跑**兜底（见 v0.4 计划 §7）。
