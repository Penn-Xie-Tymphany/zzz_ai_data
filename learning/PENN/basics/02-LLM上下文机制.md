# 02 · LLM 上下文机制：无状态、messages 重发与 KV Cache

> 是什么：澄清"AI 怎么记住对话"这个最容易被误解的地基概念。
> 为什么重要：不理解它就无法理解 agent 循环的成本、失忆、截断等一切工程问题。
> 和比赛的关联：baseline 每轮重建全部消息（react.py:83），observation 回灌导致 tokens 线性膨胀。

## 一句话结论

**LLM 是无状态的纯函数：`f(tokens) → tokens`。
所谓"记住上下文"，永远是客户端把历史完整重发一遍。API 和本地模型在这点上没有任何区别。**

## 一、"记忆"的真相：每次都全量重发

API"连续对话"的实际过程：

```
第 1 次请求:  messages = [user: 你好]                            → 回复 A
第 2 次请求:  messages = [user: 你好, assistant: A, user: 问题2]      → 回复 B
第 3 次请求:  messages = [user: 你好, assistant: A, user: 问题2, assistant: B, user: 问题3]
              ↑ 前两轮内容原封不动又发了一遍
```

服务器响应回来即忘，**不保存对话状态**。维护 `messages` 数组并全量重发是客户端代码的责任。
所以官方 baseline `_build_messages()`（react.py:83）每轮从零重建整个列表——这是唯一正确的方式，不是偷懒。

## 二、本地跑大模型时：区分三样东西

| 东西 | 在哪 | 是不是"记忆" |
| --- | --- | --- |
| **模型权重**（几十 GB） | 常驻显存 | ❌ 是模型的"知识和能力"，与具体对话无关 |
| **KV Cache** | 显存（推理框架管理） | ⚠️ 只是**计算缓存**，加速用的 |
| **对话历史** | 你的程序内存里 | ✅ 唯一的"记忆"，必须每轮显式喂给模型 |

### KV Cache 是什么

Transformer 逐 token 生成时，每个 token 会产生 Key/Value 向量供后续 token 注意力查询。
如果本次请求的前缀与上次**完全一致**（同样的 system + 历史），vLLM/Ollama 等框架可直接复用上次算好的 KV，
只计算新增部分。

**关键理解**：这是提速/省钱优化，语义上模型依然什么都"不记得"。你不传历史，它就是不知道。
API 服务商同理——DeepSeek 返回的 usage 里的字段就是证据：

```json
"prompt_cache_hit_tokens": 123,   ← 服务端识别出重复前缀，命中缓存的部分折扣计费
"prompt_cache_miss_tokens": 8     ← 新增部分全价
```

## 三、Token：LLM 的计量单位

- 模型读写的最小单位不是字/词，是 **token**（词片段）。粗略换算：英文 1 token≈4 字符，中文 1 字≈1~2 token；
- **上下文窗口** = 单次请求允许的最大 tokens 总数（输入+输出共享，如 128K）；
- 计费按 token：输入（prompt）通常比输出便宜一个量级；缓存命中更便宜；
- 超窗口 = 请求直接报错，不会自动"翻页"——裁剪历史是你自己的事。

## 四、我们自己实验的铁证 📊

task_11 跑分时每步打印的 prompt tokens：

```
step 1:  in=702      ← 只有 system + 问题
step 5:  in=5875     ← 前 4 步工具结果全部随历史重发
step 15: in=12194    ← 线性膨胀
step 17: in=15210
```

## 五、由此推出的工程事实

1. **成本线性增长、体感平方级**：第 N 轮要为 N 条历史付费 → agent 循环里 observation 必须有截断/摘要策略；
2. **"失忆"不是 bug**：想让模型记住什么，就把它放进 messages，没有其他魔法；
3. **长任务的核心矛盾**：历史越长推理越准 vs 历史越长越贵越慢越容易超窗 →
   这就是 hard/extreme 题考"上下文工程"、冠军方案做记忆管理的根本原因；
4. **多轮对话的"连续感"是客户端拼出来的幻觉**——理解这点后，任何 agent 框架的源码都不再神秘。
