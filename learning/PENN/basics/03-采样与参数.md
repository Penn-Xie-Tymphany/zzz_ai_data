# 03 · 采样参数：temperature、max_tokens 与"随机性"的真相

> 是什么：调用 LLM 时最常被误解的几个参数。
> 为什么重要：baseline 配置里就有 temperature=0.0 和 max_steps；我们实测中踩过 max_tokens 截断坑。
> 和比赛的关联：评测要可复现（temperature=0），但 temperature=0 ≠ 完全确定（实测证据见下）。

## 一、核心参数速查

| 参数 | 作用 | 我们项目里的取值 |
| --- | --- | --- |
| `temperature` | 采样随机度：0=总选概率最高的 token，越高越"敢冒险" | baseline 用 **0.0** |
| `top_p` | 核采样：只在累计概率前 p 的候选里抽 | 未设置（默认） |
| `max_tokens` | 单次回复的最大生成长度，**超了直接截断** | ⚙️ 本机补丁设 2048 |
| `stop` | 停止序列 | 未用 |
| `seed` | 部分服务商支持，试图固定采样 | DeepSeek 不保证 |

## 二、temperature 的直觉

把模型想象成每步都在给"下一个 token 的候选列表"打分：

```
temperature=0.0 : 永远选第 1 名          → 稳定、保守、适合评测/代码
temperature=0.7 : 第 1 名大概率选中，偶尔选后面的 → 日常对话默认
temperature=1.5 : 经常剑走偏锋            → 创意写作
```

**为什么评测和 agent 都用 0**：我们要的是"可靠地执行流程"，不是"有趣的多样性"。

## 三、⚠️ temperature=0 ≠ 每次结果完全一样

**实测证据**：task_11 在完全相同配置（temperature=0）下跑了多次：

| 运行 | 步数 | 结果 |
| --- | --- | --- |
| 第一次 | 17 步提交 | 全对 |
| 第二次 | 40 步耗尽失败 | 中途陷入解析错误循环 |
| 第三次 | 22 步提交 | 全对 |

原因：服务端批量推理/浮点并行计算的数值非确定性 + 服务端路由差异。
**结论**：单次跑通 ≠ 稳定跑通。评估 agent 必须多跑几遍看通过率（这正是 run-benchmark 存在的意义）。

## 四、max_tokens 截断陷阱

- 不传 max_tokens 时用服务端默认（可能很大），json 模式下模型可能生成极长内容 → 又慢又贵；
- 传太小则回复被拦腰截断 → JSON 解析必然失败。

实测：step 16 出现过 `out=2048`（正好顶到上限）——那次输出就是被截断的，下一步模型自己换了短写法重试。
**经验值**：agent 场景给 2048 足够（一步只需要 thought+一个动作），并靠错误回灌自愈偶发截断。

## 五、与上下文机制的联动

复习 [02-LLM上下文机制.md](02-LLM上下文机制.md)：每次请求 = 全量历史重新推理。
所以：
- 历史越长 → 每步越慢越贵；
- temperature 影响的是"生成"环节的随机性，不影响输入部分的计算（输入部分命中缓存的话是确定复用的）。
