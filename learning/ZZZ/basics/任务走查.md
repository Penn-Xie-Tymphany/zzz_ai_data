# 任务走查：用人类的解法，对照 agent 的解法

> **是什么**：挑一道具体题，先自己动手解一遍，再看 agent 的 trace 走了一遍什么。
> **为什么重要**：只看架构会飘在天上；走查一题，能把"工具/上下文/评分"全部落回地面。
> **和比赛的关联**：走查是发现"丢分到底丢在哪一步"的最快手段。

> ⏳ **待补写**：等环境跑通、选好题目后按下面模板填。

## 走查模板（每题一份）

### 1. 题目卡片

| 项 | 内容 |
| --- | --- |
| task_id | （如 task_11） |
| 难度 | easy / medium / hard |
| 问题原文 | （一句话概括） |
| 数据资产 | csv? json? sqlite? 文档? |
| gold 答案形状 | 行数 × 列数，列名含义 |

### 2. 我（人类）会怎么解

1. 先读什么、后读什么；
2. 关键的业务口径在哪份文档里；
3. 最终要输出哪几列、怎么聚合。

### 3. Agent 实际怎么走

| 步 | thought 要点 | action | observation 要点 |
| --- | --- | --- | --- |
| 1 | | | |
| 2 | | | |
| … | | | |

- 总步数、是否触发步数上限、是否有解析失败重试；
- 上下文量级（粗估 token）。

### 4. 对照结论

- [ ] agent 的走法与我的一致吗？不一致的地方是更优还是绕路？
- [ ] 输出列形状与 gold 是否一致（列数一致 / 多给 / 少给）？
- [ ] 丢分发生在"没解出来"还是"解出来但形状不对"？

## 走查候选题

- [ ] 一道 easy：验证最短路径，看 baseline 上限；
- [ ] 一道 medium：看 Text-to-SQL 与多源对齐；
- [ ] 一道 hard：看长文档下会不会上下文失控。
